# 文件浏览（SFTP / WSL）

涉及 `Services/IFileSystemSession.cs`、`SftpSession.cs`、`WslFileSession.cs`、`ViewModels/FileBrowserViewModel.cs`。

## 抽象

`IFileSystemOps` 是文件浏览器需要的那组操作，`IFileSystemSession` 是"一个惰性连接的会话，所有操作串行化"。两个实现：SSH 连接走 SFTP，WSL 连接走 `\wsl.localhost` UNC 路径。

**路径一律是 Unix 风格**（`/home/user`），不管后端是什么。WSL 实现在边界上做转换。

`SupportsPermissions` 为 false 时（WSL 走 9P 共享，看不到 Unix 权限）浏览器隐藏权限列和 chmod 命令。

## 为什么 SFTP 要自己拨号

SSH.NET 没有公开 API 在已有的 `SshClient` 传输上打开 SFTP 子系统通道。所以 `SftpSession` 用同样的编程凭据**另开一条连接**——而且是**惰性**的，在第一次操作时才拨号，这样从不打开文件浏览器的标签页完全不付这个代价。

代价是：文件浏览器看到的是**直连目标**，不跟随用户在终端里做的跳转。所以路径栏上显式显示 `user@host`，让这一点保持明显。

## 串行化与重连

所有操作串行化通过一个队列，原因有两个：`SftpClient` 在一条通道上并发使用不安全；串行化同时避免慢传输和目录列举互相插队（传输另有自己的会话）。

`FileSystemRetry` 是这里最重要的一个设计决定。传输死掉（空闲超时、服务器重启）时可以重拨，**但操作能不能重放只有调用方知道**：

- **`Idempotent`** —— 列目录、重开流的传输，重跑一次没问题。
- **`Once`**（可变操作的安全默认值）—— 删除或重命名可能已经在服务端生效了，只是回复没送到。第二次执行会返回"文件不存在"，于是给一个**其实成功了的操作报了失败**。

所以死传输总是被丢弃（下次操作会重拨），但只有 `Idempotent` 的操作会被重放。而且只有**传输本身在操作中途死掉**才值得一次重连重试，SFTP 层面的错误（如"没有这个文件"）不算。

`Dispose` 跑在工作线程上：释放一个活的网络客户端会阻塞，而标签页关闭时 `Dispose` 是从 UI 线程调用的。

## 浏览器面板

`FileBrowserViewModel` 用**两个**惰性连接的会话：

- **浏览会话** —— 列目录、重命名、删除。始终保持响应。
- **传输会话** —— 上传/下载顺序执行，不阻塞列目录。

其它设计点：

- **缓存 + 后台重校验。** 有缓存的列表立刻渲染，同时在后台拉新数据；数据不同且用户还在该目录时换上去，并保住选中项和焦点。显式刷新和变更后重载绕过缓存。
- **焦点管理是显式的。** 重载列表会重建每一行，如果焦点在某行上就会被静默丢掉。所以有一组由视图提供的回调（聚焦列表、选中并滚动到项、聚焦路径框并选中文本、聚焦行内重命名编辑器）。导航失败时把焦点放回路径框并保留错误路径，让用户直接改。
- **空闲回收。** 面板隐藏后，已连接的会话在空闲宽限期后回收，但**浏览中、传输中、远程编辑中绝不回收**。
- **远程编辑（F4 / 双击）。** 下载到一个按远程路径稳定映射的本地路径（重复编辑同一文件复用同一份工作副本，不堆满临时目录），用本地关联程序打开，然后监视本地文件在写入稳定后自动回传。**必须防抖**：编辑器保存是突发式的（截断+写入，或写临时文件再改名覆盖）。
- **取消传输靠在进度回调里抛异常**——SSH.NET 的传输循环没有 token 参数。
